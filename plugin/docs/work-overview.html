Přehled rozpracované práce

Historical design snapshot from 2026-09-30. References to the native GUI describe a retired surface. See the plugin README for current behavior.

Jedna tabulka přes Linear, GitHub a pohunek. Všechno v ní už někde je, jen ne pohromadě. Chybí jediný údaj: na které issue nebo PR daná session pracuje. Z toho se pak dá spočítat, kdo je na tahu. Celé to je workflow plugin pohunku podle #148, takže daemon zůstává obecný.

Závazný popis je RFC v repu machine-management: docs/work-overview/work-overview-rfc.md. Tahle stránka je jeho vizuální shrnutí.

Jak to funguje

Obecné jádro, specifický plugin

Pohunek jádro zná sessions, worktrees, projekty, tasky, události, notifikace a metadata, kterým nerozumí. Všechno o Linearu a GitHubu je v pluginu pohunek-work. Plugin si provider data načte sám svými tokeny, s pohunkem mluví přes veřejné CLI a SDK a od jádra dostane vlastní adresář pro konfiguraci a stav. Sloupec „Na tahu“ spočítá při každém čtení a nikam ho neukládá.

Chybějící vazba

Jeden klíč přes všechny systémy

Všech 255 sessions za posledních 45 dní běželo z master a žádná pohunek session pro connection nemá metadata. Spojení stojí na dvou konvencích: branch nese klíč issue a session nese work.link.*. Obojí zapíše plugin při spuštění, daemon metadata jen uloží.

Kdo je na tahu

Jediný dopočítaný sloupec

Ostatní sloupce jsou přímo hodnoty ze zdrojů. „Na tahu“ se počítá při každém čtení a vyhrává první pravidlo, které platí. Bez něj by nešlo filtrovat „jen já“ a hlavně poznat, jestli po „changes requested“ už někdo něco udělal: GitHub drží CHANGES_REQUESTED, dokud reviewer znovu neschválí.

Rozhraní

CLI, rofi, notifikace a skill

Všechna rozhraní používají stejnou knihovnu pluginu a stejné akce. Panel v GUI ve v1 není, protože #148 rozšíření nativního GUI nepovoluje. Jak data pluginu dostat do GUI nebo webu, je otevřená otázka pro v2.

Terminál

CLI pohunek-work

list, do, attach, gc, doctor. S --json slouží jako vstup pro agenty. Až jádro umí spouštět akce pluginu, bude to pohunek work ….

Rychlé

rofi pohunek-rofi-work

Dodává ho plugin. Zkratka ukáže řádky, kde jsi na tahu ty, Enter provede akci řádku.

Upozornění

pohunek-work watch

Posílá notifikaci přes notification.create jen při přechodu řádku na „Já“. Zatím jako user unit, později jako služba deklarovaná v manifestu.

Jedna issue celá

DMD-2188 krok po kroku

Tučně jsou kroky, kdy jsi na tahu ty.

  1. Přes rofi nebo CLI dáš do linear:DMD-2188 implement.ty · rofi / CLIPlugin si přes project action vyžádá profil agenta a prompt, vytvoří branch zajca/DMD-2188/coalesce-buckets a spustí session „DMD-2188“ s work.link.id a work.role=implement.
  2. Agent pracuje. Na tahu: Agent.agentPohunek eviduje aktivitu. Plugin nic nezapisuje.
  3. Agent se zasekne. Přijde notifikace, na tahu: Já: odpovědět agentovi.ty · attachPohunek agent_blocked. Po odpovědi se řádek vrátí na Agent.
  4. Agent otevře draft PR #8605 a session skončí.agentPlugin spojí PR s issue přes název branche.
  5. Na tahu: Já: pustit z draftu. Projdeš diff a AI review a dáš ready.tyGitHub.
  6. Na tahu: Reviewer.reviewerGitHub.
  7. Reviewer chce změny. Na tahu: Já: reagovat. Dáš babysit.ty · rofi / CLISession „PR-8605“ s work.role=babysit ve stejném worktree. Předchozí session už neběží.
  8. Babysit opraví, pushne, odpoví a požádá o re-review.agentPravidlo 4 to ověří přímo na GitHubu. Pokud něco chybí, zůstává na tahu Já: reagovat.
  9. Approve a zelené CI. Na tahu: Já: merge.tyGitHub. Linear integrace přepne issue na Done.
  10. post-merge najde podle work.link.id session a worktree a uklidí je.automatickyTranscript zůstává v ~/.claude/projects.

Nastavení per projekt

Soubor pro každý projekt v adresáři pluginu

Jádro kvůli nastavení per projekt nic nového nepotřebuje. Plugin má svůj config adresář a v něm jeden soubor pro každý pohunek projekt. Zdroj je verzovaný v machine-management/clients/zajca/pohunek-work/.

# config adresář pluginu
config.toml                  # identita, watch, globální [policy] a [profiles]
projects/
  connection.toml            # název souboru = label pohunek projektu

# projects/connection.toml
[project]
pohunek_label  = "connection"
repo           = "keboola/connection"
linear_team    = "DMD"
branch_pattern = "^zajca/(?P<key>DMD-[0-9]+)/"
ignored_checks = ["CD / Enqueue E2E"]
policy_checks  = []
ai_reviewers   = ["copilot-pull-request-reviewer", "chatgpt-codex-connector", "coderabbitai"]

# volitelně: přebije globální tabulku celou
[profiles]
babysit = "claude-otel"
Projekty bere plugin z registru pohunkuProjekt se v tabulce objeví, když pohunek project list --json má projekt s daným labelem, jeho origin_url odpovídá repo a existuje soubor projektu. Nesoulad, třeba po project rename, nahlásí pohunek-work doctor a projekt vynechá. Nic se nehádá.
Tabulky se nemíchají[policy] nebo [profiles] v souboru projektu přebije globální tabulku celou, stejně jako u per-project actions v pohunku. Co platí, ukáže pohunek-work config show connection i se zdrojovým souborem.
Profily jen jménem[profiles] vybírá existující profily z ~/.config/pohunek/agents/. Nikdy nedefinuje program, argumenty ani prostředí.
Bez vrstvy v repu ve v1Connection je týmové repo a politika z repa by mohla agentovi rozšířit pravomoci. Později může plugin z <repo>/.pohunek/plugins/work.toml číst jen tabulku [project], nikdy [policy] ani [profiles].
Návaznost na task RFC

Delegated task runs a dark factory

Obě RFC řeší, jak agent práci provede a jak se ověří na hostu. Plugin řeší, kdo je na tahu napříč Linearem a GitHubem. Továrna počítá s člověkem jen ve dvou bodech, attention a task.review, a oba se v tabulce objeví jako „Já“. Commit, push, PR a merge task RFC vědomě vynechává (§5), takže celá GitHubová strana zůstává na pluginu.

Směr: agent místo mě

Tabulka je vstup pro managera

Cílem je, aby práci řídil agent: vybíral další krok, volil profil a model a obsluhoval víc projektů. Je to manager z dark factory RFC. Tabulka je jeho vstup a akce, které dnes spouštíš ty, jsou tytéž operace, které pak bude volat on. Etapy A až C proto drží pět pravidel.

1. list --json je verzované APIKaždý řádek nese akce a u každé příznak, zda ji smí agent.
2. Akce jsou pojmenované operacedo <klíč> babysit|fix-ci|rebase|ready|merge, idempotentní, s kontrolou předpokladů. Deklarované i v manifestu pluginu podle #148.
3. Klíč obsahuje projektlinear:DMD-2188, github:keboola/connection#8605. Další projekt je nový soubor, ne nový kód.
4. Politika autonomie v konfiguraci, na začátku prázdnáKteré akce smí agent sám, jaký profil pro akci a projekt, limity. Volba modelu patří managerovi, daemon jen spustí zvolený profil.
5. Log akcíKdo, co, profil, výsledek a cena, pokud ji provider hlásí. Slouží k auditu a k volbě modelů.

Roadmapa

Co kde upravit, krok po kroku

Etapy A až C nečekají na nic. Plugin v nich běží jako obyčejný owner proces, což je přesně to, co #148 formalizuje. Etapa D ho zabalí podle #148 a z jádra odstraní Linear a GitHub. Etapy F a G čekají na epiky #182 a #185.
